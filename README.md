# PrintAu

Веб-портал для 3D-печати на заказ: заказчики размещают заказы, исполнители
делают ставки в формате аукциона, после выполнения заказа стороны оставляют
друг другу отзывы, которые формируют публичный рейтинг.

## Возможности

- Регистрация с ролью «Заказчик», «Исполнитель» или «3D-дизайнер/инженер»,
  вход по email/паролю.
- Заказчик создаёт заказ (материал, количество, бюджет, срок приёма ставок) и
  может приложить файлы (модели, чертежи, референсы).
- Исполнители и дизайнеры видят открытые аукционы и делают ставки (цена +
  срок + сообщение).
- Заказчик выбирает победившую ставку → заказ переходит по статусам
  `Приём ставок → Исполнитель выбран → В печати → Завершён` (или «Отменён»).
  Победивший исполнитель/дизайнер может приложить файлы с результатом работы.
- После завершения заказа обе стороны оставляют друг другу отзыв (1–5 звёзд +
  комментарий); рейтинг пользователя пересчитывается автоматически.
- Публичный профиль пользователя со всеми отзывами и (для исполнителей и
  дизайнеров) специализацией, материалами/форматами, оборудованием/ПО и ценой.
- Каталог специалистов с фильтром по роли/материалу/городу и сортировкой по
  рейтингу.
- Личный кабинет: у заказчика — список своих заказов, у исполнителя/дизайнера
  — список своих ставок.
- `/privacy` — политика конфиденциальности, в т.ч. о хранении и доступе к
  файлам, приложенным к заказам.
- `/offer` — публичная оферта (условия подписки, комиссии, оплаты).
- `/billing` — подписка портала (300 ₽/мес) и комиссия площадки (1% с
  завершённых заказов), см. раздел «Подписка и комиссия» ниже.
- `/forgot-password`, `/reset-password` — восстановление пароля по email.
- Email-уведомления: новая ставка на заказ, ставка принята, новый отзыв.

## Стек

Next.js (App Router, TypeScript) · Prisma + SQLite · Auth.js (NextAuth v5,
Credentials provider) · Tailwind CSS · Zod · Server Actions.

Роли/статусы (`Role`, `OrderStatus`, `BidStatus`) хранятся как строки в SQLite
(нет нативных enum) и типизируются на уровне TypeScript в
`src/lib/constants.ts`.

## Запуск локально

```bash
npm install
cp .env.example .env   # при необходимости поменяйте AUTH_SECRET
npm run db:migrate     # применить миграции Prisma
npm run db:seed        # заполнить демо-данными
npm run dev
```

Откройте http://localhost:3000.

## Структура

- `prisma/schema.prisma` — модели `User`, `Order`, `Bid`, `Review`, `Attachment`,
  `Subscription`, `Payment`, `PasswordResetToken`.
- `src/lib/actions/*` — server actions (регистрация/вход, заказы и ставки,
  жизненный цикл заказа, отзывы, профиль, вложения, биллинг, сброс пароля).
- `src/lib/orders.ts`, `src/lib/users.ts` — доступ к данным (Prisma-запросы).
- `src/lib/storage.ts` — сохранение/валидация/чтение файлов на диске
  (`UPLOAD_DIR`, по умолчанию `./uploads`).
- `src/lib/mail.ts` — отправка почты (SMTP через nodemailer; без настройки —
  безопасный демо-режим, письмо только логируется на сервере).
- `src/lib/rate-limit.ts` — общий in-memory rate-limit (вход, сброс пароля).
- `src/app/api/attachments/[id]/route.ts` — авторизованная выдача файлов.
- `src/app/api/health/route.ts` — health-check для Docker/аптайм-мониторинга.
- `src/app/api/internal/alert/route.ts` — приём алертов от `scripts/check-disk.sh`.
- `scripts/backup.sh`, `scripts/check-disk.sh` — бэкапы и мониторинг диска
  (см. `DEPLOY.md`).
- `src/app/*` — страницы App Router.

## Файлы (вложения к заказам)

Файлы хранятся на диске сервера (путь — `UPLOAD_DIR`, в Docker-деплое это
том `db-data`, см. `docker-compose.yml`), а не в базе. Подробности о правах
доступа к чужим файлам — в `/privacy` и в комментариях
`src/app/api/attachments/[id]/route.ts`.


## Языки и SEO

Интерфейс переведён на 7 языков (ru, en, zh, hi, es, fr, ar; арабский — с RTL).
Язык живёт **в адресе страницы**: `/en/auctions`, `/zh/materials`. Это принципиально
для международного SEO — без отдельного URL на язык поисковик видит один адрес с
меняющимся содержимым и не может показать пользователю его языковую версию.

Как это устроено:

- `src/middleware.ts` — снимает языковой префикс, отдаёт приложению плоский
  маршрут и прокидывает локаль заголовком. Адрес без префикса получает
  постоянный редирект (308) на префиксованный, чтобы у страницы был ровно один
  канонический адрес.
- `src/components/LocaleLink.tsx` — замена `next/link`, дописывающая префикс:
  внутренние ссылки не теряют язык и не стоят лишнего редиректа.
- `src/lib/i18n/redirect.ts` — `localeRedirect()` вместо `redirect()` на серверe:
  редирект из серверного экшена роутер отрабатывает на клиенте, и префикс при
  обычном `redirect()` терялся бы.
- `src/lib/seo.ts` — тексты `<title>`/`<description>` под поисковые запросы на
  каждом языке, canonical, hreflang (все языки + `x-default`), Open Graph и
  Twitter-карточки.
- `src/app/sitemap.ts` — карта сайта «страница × язык» с блоками alternates,
  включая открытые аукционы и профили специалистов.
- `src/app/robots.ts` — личные разделы (кабинет, оплата, админка, профиль,
  формы входа) закрыты от обхода; там же ссылка на карту сайта.
- Разметка Schema.org (`Organization`, `WebSite` + `SearchAction`) в корневом
  layout.

Публичный адрес сайта для canonical/sitemap берётся из `APP_URL` (или из
настроек в админке). **Задайте его перед публикацией** — иначе адреса в карте
сайта соберутся из заголовков запроса.

## Админка

`/admin/settings` (доступно только роли `ADMIN`, ссылка появляется в шапке
после входа под таким аккаунтом) — панель, где можно поменять большинство
параметров ниже (цену подписки, комиссию, ключи ЮKassa, SMTP, алерты,
`APP_URL`) прямо на живом сайте, без правки `.env` и передеплоя. Значение из
админки всегда побеждает `.env`; если поле в админке не задано — берётся
`.env`, а если нет и там — встроенное значение по умолчанию.

Самостоятельная регистрация с ролью ADMIN запрещена — единственный
предустановленный админ-аккаунт создаётся сидом: `admin@example.com` /
`password123` (см. `prisma/seed.ts`). **Смените пароль сразу после первого
входа на боевом инстансе** — это делается на `/profile/edit`, как для любого
другого аккаунта.

Три переменные в `.env` в админке принципиально не редактируются —
`DATABASE_URL`, `AUTH_SECRET`, `UPLOAD_DIR` — их смена требует перезапуска
контейнера, а не формы в браузере.

## Подписка и комиссия

Модель монетизации: подписка 300 ₽/мес с каждого пользователя + комиссия
площадки 1% с цены принятой ставки по каждому завершённому заказу (списывается
с исполнителя/дизайнера). Значения по умолчанию — константы
`SUBSCRIPTION_PRICE_RUB`, `SUBSCRIPTION_PERIOD_DAYS`, `COMMISSION_RATE` в
`src/lib/constants.ts`, но их удобнее менять через `/admin/settings` (см.
выше), не трогая код.

**Без настройки платёжного провайдера всё уже работает в демо-режиме** —
кнопка «Оплатить» на `/billing` сразу помечает платёж оплаченным, без
реального списания денег. Так можно проверить весь сценарий (начисление
комиссии при завершении заказа, продление подписки и т.д.) без реквизитов.

По умолчанию подписка **не блокирует** создание заказов/ставок — она
считается и показывается, но неактивная подписка ни на что не влияет. Чтобы
включить платный гейт: `SUBSCRIPTION_ENFORCEMENT=true`.

### Фискальные чеки (54-ФЗ)

При приёме денег от физического лица ИП/ООО обязаны выдать покупателю
фискальный чек. Своя онлайн-касса не нужна: чек пробивает ЮKassa — в платёж
передаётся состав заказа, email плательщика и коды системы налогообложения и
НДС (`receipt` в `src/lib/payments/yookassa.ts`).

Что нужно сделать при подключении реальной оплаты:

1. Подключить услугу «Чеки от ЮKassa» в личном кабинете магазина.
2. В `/admin/settings` → «Фискальные чеки» выбрать систему налогообложения и
   ставку НДС. Для ИП на УСН это обычно «УСН «Доходы»» и «Без НДС» — они и
   стоят по умолчанию.

Чек уходит на email, указанный пользователем при регистрации. Позиция чека —
услуга, оплаченная целиком (`payment_subject: service`,
`payment_mode: full_payment`), что соответствует и подписке, и комиссии
площадки.

### Подключение реальной оплаты (ЮKassa)

1. Зарегистрируйте магазин на [yookassa.ru](https://yookassa.ru) (нужен
   ИП/ООО) и получите `shopId` и секретный ключ.
2. Задайте переменные окружения:
   ```
   YOOKASSA_SHOP_ID=...
   YOOKASSA_SECRET_KEY=...
   APP_URL=https://your-domain.example   # публичный адрес сайта
   ```
3. В личном кабинете ЮKassa укажите URL для уведомлений (webhook):
   `https://your-domain.example/api/payments/yookassa/webhook`.
4. Готово — `/billing` автоматически переключится с демо-режима на реальные
   платежи (redirect на страницу оплаты ЮKassa).

Вебхук не доверяет телу запроса напрямую: при получении уведомления сервер
перезапрашивает статус платежа у ЮKassa по id через авторизованный запрос
собственным секретным ключом и только тогда помечает платёж оплаченным —
см. `src/app/api/payments/yookassa/webhook/route.ts`.

Другие провайдеры (CloudPayments, Robokassa и т.п.) не подключены — при
необходимости смена провайдера ограничивается файлом
`src/lib/payments/yookassa.ts` и вызовами в `src/lib/actions/billing.ts`.

## Восстановление пароля

`/forgot-password` → `/reset-password`. Токен сброса — случайные 32 байта,
в базе хранится только его sha256-хэш (как и пароли — в виде bcrypt-хэша,
не в открытом виде), ссылка одноразовая и живёт 1 час. Ответ на запрос
сброса всегда одинаковый независимо от того, зарегистрирован ли email —
иначе форма превращается в инструмент проверки чужих email на площадке.

**Без настроенного SMTP письмо не отправляется, а только логируется на
сервере** (`docker compose logs app` / `npm run dev` вывод) — ссылку из лога
можно использовать для тестирования, но реальным пользователям она так не
дойдёт. Задайте `SMTP_HOST`/`SMTP_PORT`/`SMTP_USER`/`SMTP_PASS`/`MAIL_FROM`
(см. `.env.example`), чтобы письма реально отправлялись — подойдёт SMTP от
Яндекс 360, Mail.ru для бизнеса, SendGrid и т.п.

Известное ограничение: смена пароля не отзывает уже выданные сессии
(NextAuth использует JWT-сессии без серверного хранилища сессий) — если у
злоумышленника была активна чужая сессия до сброса пароля, она останется
активной и после. Для небольшой площадки это принятый компромисс; полноценное
решение потребовало бы перехода на database-сессии.
