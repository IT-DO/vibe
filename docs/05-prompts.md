# Готовые промпты

Копируй, подставляй своё, отправляй Claude. Это не магические заклинания —
просто хорошо поставленные задачи. Со временем начнёшь писать такие сам,
и этот файл станет не нужен.

Общее правило: **сначала прочитай, что тебе предлагают, потом соглашайся.**

---

## Каждый день

### Разобраться, что вообще происходит

```
Объясни простыми словами, что делает файл src/lib/credits.ts.
Я не программист. Расскажи так, будто объясняешь коллеге без
технического образования, и приведи пример, когда этот файл
участвует в работе сайта.
```

### Перед тем, как что-то менять

```
Я хочу [описание задачи].
Не пиши код. Сначала расскажи: какие файлы придётся тронуть,
что может сломаться и есть ли способ проще. Дождись моего «ок».
```

### После изменений

```
Перечисли, что именно ты изменил: файлы и что в каждом.
Что может сломаться из-за этого? Прогони npm run smoke и покажи результат.
```

### Когда что-то упало

```
Запустил [команда]. Вот вывод целиком:

[вставь ВЕСЬ текст ошибки, не сокращая]

Что это значит и как починить?
```

> Ошибку вставляй целиком. В сообщениях об ошибках важна каждая строка,
> а самое полезное часто в середине, а не в конце.

### Когда чинится по кругу

```
Мы пытаемся починить это третий раз, и каждый раз ломается что-то другое.
Откатываемся. Объясни, почему это не получается, и предложи другой подход.
```

## Развитие продукта

### История генераций

```
Добавь страницу /history — список карточек текущего пользователя.
Свежие сверху, по 20 штук, кнопка «Показать ещё».
В строке: дата, название товара, кнопка «Открыть» — разворачивает
полный текст прямо в списке.
Данные бери из таблицы generations, поля input и output — это JSON.
Чужие генерации не должны быть видны ни при каких условиях.
Добавь ссылку на /history в шапку рядом с «Кабинет».
Допиши в scripts/smoke.mjs проверку, что чужие генерации не видны.
```

### Пакетная генерация

```
Добавь в кабинет вкладку «Несколько сразу»: пользователь вставляет
список товаров, по одному в строке, и получает карточки для всех.
Условия:
- максимум 20 строк за раз;
- кредиты списываются по одной за строку, и только за те, что успешно
  сгенерировались;
- если одна упала, остальные всё равно должны отработать;
- показывай прогресс: «готово 3 из 10»;
- в конце — кнопка «Скачать всё в CSV».
Добавь проверку в scripts/smoke.mjs.
```

### Выгрузка в Excel

```
Добавь на страницу результата кнопку «Скачать XLSX».
Один товар — одна строка, колонки: Заголовок, Буллеты (через перенос
строки в ячейке), Описание, Ключевые слова, Поисковые запросы.
Файл должен открываться в Excel без вопросов про кодировку —
кириллица не должна превратиться в кракозябры.
Скажи, какую библиотеку добавляешь и почему именно её.
```

### Промокоды

```
Добавь промокоды на скидку при покупке пакета.
- Таблица promo_codes: код, процент скидки, сколько раз можно
  использовать, до какой даты действует, сколько уже использовали.
- Поле ввода кода на странице тарифов, пересчёт цены до перехода к оплате.
- Просроченный, исчерпанный или несуществующий код — понятная ошибка.
- Один пользователь может применить один и тот же код только один раз.
Сначала опиши план, код не пиши.
```

### Письмо после регистрации

```
Добавь отправку письма при регистрации: короткое приветствие
и ссылка на кабинет.
Настройки SMTP брать из .env, дополни .env.example.
Важно: если письмо не отправилось, регистрация всё равно должна
пройти успешно — человек не должен терять аккаунт из-за почты.
Ошибку отправки просто запиши в лог.
```

## Промпт продукта

**Промпт уже написан** — он приехал вместе с проектом. Сочинять его
с нуля не нужно, это не пропущенный шаг.

Лежит он в файле `src/lib/llm.ts`, в константе `SYSTEM_PROMPT`. Это
обычный текст на русском: правила о том, как писать заголовок, буллеты
и ключевые слова. Открывается любым редактором, правится как письмо —
никакого программирования.

Твоя работа не написать его, а **докрутить на реальных товарах**: прогнал
десять штук, прочитал результат глазами покупателя, поправил формулировку,
прогнал снова.

### Улучшить качество текстов

```
Вот промпт из src/lib/llm.ts: [вставь]
Вот что он выдал на реальном товаре: [вставь результат]
Проблемы: [например: буллеты общие и подходят любому товару;
заголовок не содержит ключевого слова; описание похоже на инструкцию].
Перепиши промпт так, чтобы этого не было. Объясни каждое изменение.
```

### Проверить промпт на десяти товарах

Такой скрипт уже есть — писать его не надо:

```bash
sudo ./try-prompt.sh              # все 10 товаров
sudo ./try-prompt.sh --only 3     # только третий, быстро и дёшево
```

### Где это запускать

Два места на выбор.

**На сервере — ничего ставить не надо.** Node там нет, но есть Docker,
и обёртка берёт Node из готового образа на время запуска:

```bash
cd /opt/app && sudo ./try-prompt.sh
```

Отчёты лягут в `/opt/app/prompt-runs/`. Скачать их на ноутбук поможет
команда, которую скрипт напечатает в конце.

**На ноутбуке — если поставишь Node 22.** Тогда правки промпта и прогон
идут в одном окне, без ssh:

```bash
npm run try-prompt
```

Оба способа делают одно и то же и читают один и тот же `.env`.


Прогоняет промпт по набору из `scripts/products.json` (десять товаров
из разных категорий — одежда, электроника, косметика, инструменты,
детское, зоотовары) и складывает результат в `prompt-runs/` файлом
с датой в имени. Правишь `SYSTEM_PROMPT` в `src/lib/llm.ts`, гоняешь
снова — и открываешь два отчёта рядом.

Заодно он сам отмечает формальные огрехи: заголовок длиннее 100 символов,
буллетов не пять, описание короче 1200 знаков, ключевых слов меньше 20,
и подозрение, что ключевые слова набиты падежами одного корня вместо
настоящих синонимов.

> С настоящей моделью каждый прогон — десять платных запросов.
> Пока привыкаешь к формату, держи `LLM_PROVIDER=mock`.

Свои товары добавляй прямо в `scripts/products.json` — это обычный
список, редактируется как текст. **Держи набор постоянным**: смысл
в том, чтобы сравнивать на одних и тех же примерах.

### Новый тип продукта

```
Добавь в кабинет второй инструмент: «Ответ на отзыв».
Пользователь вставляет текст отзыва покупателя и оценку (1-5),
получает три варианта вежливого ответа от лица продавца.
Стоимость — 1 кредит, как у карточки.
Сделай по образцу существующей генерации: та же схема списания,
та же обработка ошибок. Промпт вынеси отдельной константой рядом
с SYSTEM_PROMPT.
Добавь проверку в scripts/smoke.mjs.
```

## Деньги и безопасность

Для этих задач **всегда** сначала проси план.

### Проверить биллинг

```
Проверь всю цепочку оплаты: BuyButton → checkout → вебхук → начисление.
Ответь по пунктам:
1. Что будет, если ЮKassa пришлёт уведомление об одном платеже трижды?
2. Что будет, если два запроса на генерацию придут одновременно,
   а на счету остался один кредит?
3. Может ли кто-то получить кредиты, не заплатив?
4. Что будет, если человек нажмёт «Оплатить» пять раз подряд?
Если где-то дыра — покажи, где именно в коде, и предложи исправление.
Код пока не меняй.
```

### Посмотреть цифры

```
Покажи команду, которая выведет из базы data/app.db:
- сколько всего пользователей;
- сколько сделали хотя бы одну генерацию;
- сколько потратили все бесплатные кредиты;
- сколько заплатили хотя бы раз;
- сумма всех успешных платежей.
Просто команду для терминала, менять код не надо.
```

### Начислить кредиты вручную

```
Покажи команду, которая начислит 30 кредитов пользователю
с почтой user@example.ru в базе data/app.db.
Команда должна ничего не делать, если такого пользователя нет.
```

### Перед показом людям

```
Проверь проект на типичные дыры перед запуском:
- может ли пользователь увидеть чужие данные;
- есть ли ограничение частоты на всех тяжёлых запросах;
- не попадают ли ключи и пароли в логи;
- что произойдёт, если отправить в формы очень длинный текст
  или кусок HTML.
Ответь списком: что проверил и что нашёл. Пока не чини.
```

## Что помогает всегда

**Проси объяснить простыми словами.** «Я не программист, объясни как
коллеге без техобразования» — работает.

**Проси план до кода** для всего, что дороже пяти минут.

**Приноси факты, а не пересказ.** Вместо «не работает оплата» —
логи, текст ошибки, номер платежа, что именно нажимал.

**Проси дописывать smoke-тест.** Каждая новая функция должна попадать
под автоматический присмотр, иначе через месяц ты не будешь знать,
что из этого ещё живо.

**Не соглашайся на непонятное.** Если ты не понимаешь, что делает
изменение, — это не твоя проблема, это плохое объяснение. Спрашивай ещё раз.
