# Как вайбкодить

Вайбкодинг — это когда ты описываешь словами, что должно получиться,
а код пишет нейросеть. Ты не перестаёшь быть главным: ты остаёшься тем,
кто решает, что делать, и проверяет, что получилось. Меняется только одно —
ты больше не набираешь код руками.

Отсюда следует главное правило, из которого растёт всё остальное:

> **Нейросеть отвечает за код. Ты отвечаешь за то, что код работает.**

Человек, который этого не понял, через две недели имеет 8000 строк, которые
он не может ни починить, ни выбросить. Человек, который понял, — имеет
работающий сервис. Разница не в навыке программирования. Разница в дисциплине
проверки.

---

## Петля, в которой ты будешь жить

Всё сводится к четырём шагам. Каждый круг — 10–40 минут.

```
1. ОПИСАТЬ     Одна задача. Понятными словами. Со всеми условиями.
      ↓
2. ПОЛУЧИТЬ    Claude пишет код.
      ↓
3. ПРОВЕРИТЬ   npm run smoke + открыть глазами в браузере.
      ↓
4. ЗАФИКСИРОВАТЬ   git commit. Точка возврата.
      ↓
    (на следующий круг)
```

Шаг 3 пропускать нельзя. Шаг 4 пропускать нельзя. Всё остальное обсуждаемо.

Почему именно так: пока изменение маленькое и проверено, откатить его —
одна команда. Когда непроверенных изменений накопилось на три дня, разбираться,
какое из них сломало оплату, будешь неделю.

## Шаг 1. Как ставить задачу

Плохая постановка — самая частая причина плохого результата. Не потому,
что нейросеть глупая, а потому что она достраивает недосказанное по-своему,
и её догадка не совпадает с твоей.

### Формула

**Что должно получиться** + **где это в проекте** + **при каких условиях** +
**как понять, что вышло правильно**.

### Сравни

> ❌ «Сделай историю генераций»

Что здесь не так: непонятно, где показывать, сколько записей, что делать
со старыми, можно ли их удалять, видно ли чужие. Claude придумает ответы сам,
и половина не совпадёт с твоими ожиданиями.

> ✅ «Добавь страницу /history — список карточек, которые сделал текущий
> пользователь. Свежие сверху, по 20 на странице, с кнопкой «Показать ещё».
> В каждой строке: дата, название товара, кнопка «Открыть» — она разворачивает
> полный текст прямо в списке. Данные брать из таблицы generations, поле input
> и output — это JSON. Чужие генерации показывать нельзя ни при каких условиях.
> Добавь ссылку на /history в шапку рядом с «Кабинет». Дополни scripts/smoke.mjs
> проверкой, что чужие генерации не видны.»

Второе занимает минуту на написание и экономит час на переделках.

### Что почти всегда стоит добавить

- **«Не трогай ничего, кроме …»** — если боишься, что зацепит соседнее.
- **«Сначала объясни, что собираешься сделать, и дождись моего "ок"»** —
  для всего, что касается денег, паролей и базы. Дешевле прочитать план,
  чем откатывать сделанное.
- **«Добавь проверку в scripts/smoke.mjs»** — чтобы новая функция сразу
  попала под автоматический присмотр.
- **«Объясни своё решение простыми словами, я не программист»** — не стесняйся.
  Это не глупый вопрос, это нормальная приёмка работы.

## Шаг 3. Проверка — твой главный навык

Ты не читаешь код. Ты проверяешь **поведение**. Это доступно кому угодно,
и именно это отличает работающий проект от кучи мусора.

### Три уровня, по возрастанию усилий

**Уровень 1. Автоматика (5 секунд).**

```bash
npm run smoke
```

Прогоняет весь путь пользователя: регистрация → генерация → списание →
запрет без кредитов → защита оплаты. Если написано «Всё хорошо» — базовые
вещи целы.

**Уровень 2. Глазами (2 минуты).** Открой браузер и **сам сделай то, что
изменилось**. Не «выглядит нормально», а нажми, введи, отправь.

**Уровень 3. Злым пользователем (5 минут).** Только для важного — оплата,
доступы, чужие данные. Попробуй сломать нарочно:

- отправить пустую форму;
- ввести текст на 10 000 символов;
- нажать кнопку два раза подряд быстро;
- открыть чужую страницу, поменяв цифру в адресе;
- нажать «Назад» в браузере после оплаты и оплатить ещё раз.

Половина реальных дыр в самодельных сервисах находится ровно этими пятью
действиями.

### Вопросы, которые стоит задавать Claude

Ты имеешь право не понимать код и при этом требовать отчёта:

- «Что именно ты изменил? Перечисли файлы и что в каждом.»
- «Что может сломаться из-за этого изменения?»
- «Что будет, если два человека нажмут эту кнопку одновременно?»
- «Может ли пользователь получить доступ к чужим данным через это?»
- «Это точно работает? Ты проверял или предполагаешь?»

Последний вопрос — самый полезный. Формулировки вроде «должно работать»,
«теперь всё в порядке» без запуска проверки — сигнал притормозить и попросить
реально запустить.

## Шаг 4. Git — это кнопка «отменить»

Git пугает названием, но тебе нужны ровно четыре команды.

```bash
# Сохранить текущее состояние как точку возврата
git add -A && git commit -m "Добавил историю генераций"

# Посмотреть, что изменилось с прошлой точки
git status

# ОТКАТИТЬ всё несохранённое — если нейросеть всё сломала
git restore .

# Вернуться к предыдущей точке целиком
git log --oneline        # смотришь список, копируешь код нужной строки
git reset --hard <код>
```

**Делай коммит после каждой удачной проверки.** Это займёт три секунды и
однажды спасёт тебе вечер. Правило простое: заработало → зафиксировал.

Ещё лучше — заведи привычку начинать так: «Прежде чем менять, скажи мне,
что собираешься сделать». Тогда откатывать придётся реже.

## Где вайбкодинг ломается

Честный список. Здесь нейросеть уверенно выдаёт правдоподобный результат,
который не работает — а ты не заметишь, потому что не читаешь код.

**Деньги.** Начисление, списание, возвраты, вебхуки. Классическая беда —
двойное начисление: платёжная система прислала уведомление дважды, а кредиты
начислились два раза. В этом проекте защита уже стоит (`credits_issued`
в таблице платежей), но если будешь трогать биллинг — проси Claude отдельно
объяснить, что будет при повторной доставке уведомления.

**Права доступа.** «Может ли Вася открыть карточку Пети?» Нейросеть пишет
код под сценарий, который ты описал, а описал ты обычно честный сценарий.
Каждый раз, когда появляется страница с чужими данными, спрашивай прямо:
«кто ещё может это открыть?»

**Одновременность.** Два запроса в одну секунду. Баланс уходит в минус,
запись задваивается. Проявляется только на реальных пользователях, то есть
уже после того, как ты порадовался запуску.

**Придуманные библиотеки и методы.** Иногда предлагается пакет, которого
нет, или метод, которого у библиотеки нет. Ловится мгновенно: `npm run build`
падает с ошибкой. Просто покажи ошибку Claude — починит.

**Устаревшие способы.** Модель помнит, как делали год назад. Иногда это
уже не так. Признак — «странно, в интернете пишут иначе». Скажи: «проверь
в актуальной документации, а не по памяти».

**Вывод не в том, что нейросеть плоха, а в том, где ставить проверку.**
Всё, что касается денег и чужих данных, проверяй руками и требуй объяснений.
Вёрстку и тексты можно принимать на глаз.

## Как не утонуть в собственном проекте

**Одна задача за раз.** «Добавь историю и почини шапку и поменяй цены» —
получишь три половинчатых изменения, и непонятно, какое сломало smoke.

**Маленькие шаги.** Лучше пять кругов петли по 15 минут, чем один на два часа.
Ошибка в маленьком шаге ищется за минуту.

**Если два раза не починилось — меняй подход.** Симптом «чиню одно, ломается
другое» означает, что задача поставлена неудачно. Не проси в третий раз то же
самое. Скажи: «Откатываемся. Объясни, почему это не получается, и предложи
другой путь».

**Заведи файл CLAUDE.md** в корне проекта и складывай туда решения, которые
не хочешь повторять каждый раз:

```markdown
# О проекте
Сервис генерации карточек товаров для WB и Ozon. Аудитория — селлеры, РФ.

# Правила
- Все тексты интерфейса — на русском, обращение на «ты».
- Цены только в src/lib/plans.ts, больше нигде не хардкодить.
- Любое изменение в биллинге — сначала план, потом код.
- После каждого изменения дополняй scripts/smoke.mjs.
- Не добавляй новые библиотеки без объяснения, зачем.
```

Claude Code читает этот файл сам. Это экономит десятки повторяющихся объяснений.

**Не переписывай то, что работает.** Соблазн «а давай сделаем красиво»
велик. Пока сервис не приносит денег, красота внутри не имеет значения.
