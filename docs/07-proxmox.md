# Хостинг на своём железе (Proxmox)

Proxmox VE — это операционная система, которая превращает один физический
компьютер в несколько виртуальных. Ставится на голое железо, управляется
через сайт в браузере. Актуальная версия — 9.2 (май 2026), основана
на Debian 13 «Trixie».

---

## Сначала честно: стоит ли

Своё железо у себя дома — отличная штука для разработки и для второго,
тестового сервера. Для **боевого сервиса, который принимает деньги**,
у него есть четыре риска, которых нет у арендованного VPS:

| Риск | Что происходит | Чем лечится |
|---|---|---|
| Электричество | Выключили свет — сервис лежит, пока тебя нет дома | ИБП минут на 20 + автозапуск |
| Домашний интернет | Провайдер не даёт «белый» IP или режет порты 80/443 | Белый IP за доплату или VPS-посредник (ниже) |
| Никакого SLA | Роутер завис в понедельник, ты вернулся в пятницу | Удалённое управление питанием |
| Железо | Диск умер — умерла база с платежами | Бэкапы наружу, обязательно |

Рабочая схема на первое время: **боевой сервис — на дешёвом VPS в России
(300–500 ₽/мес), Proxmox дома — под разработку и тесты.** Тогда падение
домашнего интернета не стоит тебе клиентов.

Если всё же хочешь боевой дома — дальше написано, как сделать это правильно.
Просто заложи ИБП и удалённую розетку в бюджет, они дешевле одного потерянного
клиента.

**Важно про закон.** Машина должна физически стоять в России: база с почтами
пользователей — это персональные данные россиян, и 152-ФЗ требует хранить
их в РФ. Домашний сервер в российской квартире это требование выполняет,
за границей — нарушает. Подробнее — в [docs/06-legal.md](06-legal.md).

---

## Виртуальная машина, а не LXC-контейнер

Proxmox умеет два вида «коробок»: полноценные виртуалки (VM) и лёгкие
контейнеры (LXC). Наш сервис ездит в Docker, и здесь важно:

> **Делай VM. Не LXC.**

Docker внутри LXC — это контейнеры внутри контейнеров. Технически заводится,
но Proxmox официально такую связку не тестирует и не поддерживает, а ломается
она обычно при обновлении — то есть в самый неудачный момент. VM ест примерно
на гигабайт памяти больше и теряет 5–15 % процессора. За предсказуемость
это дёшево.

Плюс в VM твой `docker-compose.yml` и `deploy.sh` работают ровно так,
как написано в [docs/03-deploy.md](03-deploy.md) — ничего не надо менять.

## Всё за один заход

Если не хочешь разбираться в деталях — вот вся последовательность.
Три команды на хосте Proxmox, четыре внутри машины.

### На хосте Proxmox

```bash
git clone -b claude/vibecoding-saas-service-mx3k2z \
  https://github.com/IT-DO/vibe.git /root/vibe
cd /root/vibe

./proxmox-create-vm.sh --plan 192.168.10.100   # посмотреть, что будет
./proxmox-create-vm.sh 192.168.10.100          # создать
```

Вместо `192.168.10.100` подставь **свободный** адрес в своей сети.
Скрипт сам подберёт номер машины, найдёт хранилище и шлюз, скачает
облачный образ Debian 13, создаст машину на 2 ядра / 4 ГБ / 32 ГБ,
включит автозапуск при включении хоста и спросит пароль.

Облачный образ — это готовый Debian, который не надо устанавливать:
машина загружается сразу настроенной. Установщик проходить не нужно.

### Внутри машины

```bash
ssh admin@192.168.10.100
```

```bash
sudo apt update && sudo apt install -y git qemu-guest-agent
sudo systemctl enable --now qemu-guest-agent

sudo git clone -b claude/vibecoding-saas-service-mx3k2z \
  https://github.com/IT-DO/vibe.git /opt/app
cd /opt/app
sudo ./install-server.sh
```

В конце установщик сам покажет состояние машины. Всё, что помечено
`[FAIL]`, — это то, что надо чинить; `[ ?? ]` на этом этапе нормально
(нет домена, нет ключей ЮKassa, тексты пока заглушка).

### Посмотреть результат

На **ноутбуке**, не на сервере:

```bash
ssh -L 3000:127.0.0.1:3000 admin@192.168.10.100
```

Пока окно открыто, сервис доступен на <http://localhost:3000>.

### Если надо начать заново

На хосте Proxmox:

```bash
qm stop НОМЕР && qm destroy НОМЕР
```

## Создать виртуалку вручную


Предполагаю, что Proxmox уже установлен и его панель открывается
в браузере по адресу вида `https://192.168.1.10:8006`.

### 1. Загрузить образ Debian

В панели: **local (имя-узла) → ISO Images → Download from URL**.
Возьми ссылку на netinst-образ Debian 13 с debian.org.

### 2. Создать VM

Кнопка **Create VM** справа сверху.

| Вкладка | Что поставить |
|---|---|
| General | Name: `kartochka`. Запомни номер VM ID — он понадобится |
| OS | Тот ISO, что скачал |
| System | Qemu Agent — **включить** (даст Proxmox видеть IP и корректно гасить машину) |
| Disks | 32 ГБ. Discard — включить, если диск SSD |
| CPU | 2 ядра |
| Memory | 4096 МБ. Balloon можно выключить — база в SQLite любит стабильную память |
| Network | Bridge `vmbr0` — виртуалка получит адрес в твоей домашней сети |

Запусти, открой **Console** и поставь Debian обычным способом.
Из галочек в конце установки нужны только **SSH server** и **standard
system utilities** — графическую оболочку не ставь, она тут лишняя.

### 3. После установки

Зайди в консоль машины и поставь гостевой агент:

```bash
apt update && apt install -y qemu-guest-agent sqlite3
systemctl enable --now qemu-guest-agent
```

`sqlite3` нужен для честных бэкапов базы — почему именно, ниже.

Узнай адрес машины:

```bash
ip -4 addr show | grep inet
```

**Закрепи этот адрес за машиной в роутере** (обычно это называется
DHCP reservation или «статический DHCP»), иначе после перезагрузки роутера
он поменяется и проброс портов перестанет работать.

### 4. Поставить сервис

С этого места виртуалка ничем не отличается от арендованного сервера.
Забери код и запусти установщик:

```bash
apt update && apt install -y git
git clone АДРЕС_ТВОЕГО_РЕПОЗИТОРИЯ /opt/app
cd /opt/app

./install-server.sh --plan     # посмотреть, что он собирается сделать
./install-server.sh            # сделать
```

Установщик ставит Docker и нужные пакеты, создаёт `.env` со случайным
`SESSION_SECRET`, вешает ночной бэкап в cron, собирает и запускает сервис.
Он безопасен при повторном запуске: уже настроенное не трогает и **никогда
не перезаписывает существующий `.env`**.

Привычка смотреть `--plan` перед запуском — та же, что и в работе
с нейросетью: сначала план, потом действие.

Если хочешь пройти те же шаги руками, они расписаны
в [docs/03-deploy.md](03-deploy.md).

### Посмотреть сервис со своего ноутбука

Сервис намеренно не торчит в сеть напрямую — он слушает только
`127.0.0.1`, а наружу его выпустит Caddy, когда будет домен.
Чтобы глянуть раньше, пробрось порт по SSH. Команда выполняется
**на ноутбуке**, не на сервере:

```bash
ssh -L 3000:127.0.0.1:3000 root@АДРЕС_ВИРТУАЛКИ
```

Пока это окно открыто, сервис доступен на ноутбуке
по адресу <http://localhost:3000>.

### 5. Проверить, что получилось

Когда закончишь, запусти на виртуалке из папки проекта:

```bash
./check-server.sh
```

Скрипт осматривает машину и печатает список: что готово, чего не хватает,
что настроено неправильно. Он ничего не меняет — только смотрит, так что
запускать можно сколько угодно раз.

Полезные вещи, которые он ловит сам: что ты случайно сделал LXC вместо VM,
что не установлен `sqlite3`, что `YOOKASSA_VERIFY_IP` остался в `false`,
что ночной бэкап не работает уже двое суток, и какой у тебя внешний IP —
чтобы понять, нужен тебе вариант А или Б из раздела ниже.

**Значения секретов он не печатает** — только факт, что переменная заполнена.
Вывод можно целиком показать Claude и спросить, что делать дальше.

## Как пустить пользователей внутрь

Это главная сложность домашнего хостинга. Сервис работает на машине
в твоей квартире, а зайти на него должны из интернета.

### Вариант А. Белый IP + проброс портов (если провайдер даёт)

Самый простой и быстрый путь.

1. Спроси у провайдера **статический «белый» IP**. Обычно это 100–200 ₽
   в месяц, подключается заявкой.
2. В роутере настрой проброс: внешний порт **80** → адрес виртуалки, порт 80;
   внешний **443** → её же порт 443.
3. В настройках домена сделай A-запись на этот белый IP.

Проверить, что снаружи видно:

```bash
# с телефона по мобильному интернету, не по домашнему Wi-Fi
curl -I http://ТВОЙ_БЕЛЫЙ_IP
```

Если провайдер дал «серый» адрес (за NAT провайдера, он же CGNAT),
проброс работать не будет в принципе — тебе нужен вариант Б.

### Вариант Б. Дешёвый VPS как парадная дверь

Схема: маленький VPS в России держит белый IP и HTTPS, а трафик уводит
по шифрованному туннелю на твою домашнюю машину. **Данные при этом
остаются дома** — VPS только передаёт запросы дальше.

```
     интернет
         │
         ▼
  ┌──────────────┐   WireGuard    ┌────────────────────┐
  │ VPS в РФ     │───(туннель)───▶│ Proxmox дома       │
  │ 300 ₽/мес    │                │ VM с сервисом      │
  │ белый IP     │                │ база лежит здесь   │
  │ Caddy: HTTPS │                │                    │
  └──────────────┘                └────────────────────┘
```

Что нужно: WireGuard на обеих сторонах и Caddy на VPS, который проксирует
на адрес домашней машины внутри туннеля. Работает при любом провайдере,
включая CGNAT, и заодно прячет твой домашний IP.

Готовая формулировка задачи для Claude:

```
Настрой доступ к моему сервису по схеме: дешёвый VPS с белым IP как
парадная дверь, домашняя виртуалка с приложением за WireGuard-туннелем.
На VPS: WireGuard-сервер и Caddy, который держит HTTPS для домена
твой-домен.ру и проксирует на адрес домашней машины внутри туннеля.
Дома: WireGuard-клиент с постоянным подключением (persistent keepalive),
приложение слушает только внутри туннеля и не торчит в домашнюю сеть.
Дай пошагово команды для обеих сторон и объясни, что делает каждая.
Я не программист.
```

### Чего не делать: Cloudflare Tunnel

В обычных руководствах по домашнему хостингу первым делом советуют
Cloudflare Tunnel. **Тебе он не подходит.** Роскомнадзор рекомендует
владельцам сайтов отказаться от Cloudflare (претензии к протоколу TLS ECH),
и доступность таких сайтов для российских пользователей нестабильна.
Твоя аудитория — продавцы маркетплейсов в России, то есть ровно те,
до кого сайт может не доехать.

## HTTPS

Caddy получает сертификат сам, но ему нужно, чтобы снаружи был доступен
порт 80 — по нему проходит проверка владения доменом.

- Вариант А (белый IP): порт 80 проброшен, всё работает само.
- Вариант Б (VPS): Caddy живёт на VPS, там с портами всё в порядке.

Если провайдер режет 80-й порт (бывает на домашних тарифах), проверку
можно проводить через DNS. Скажи Claude: «провайдер блокирует порт 80,
настрой Caddy на проверку через DNS у моего регистратора домена».

## Снапшоты — то, ради чего стоит терпеть Proxmox

Вот это по-настоящему полезно именно тебе.

Перед любым рискованным изменением делаешь снимок всей машины целиком.
Сломалось — откатываешься за полминуты в состояние «как было», вместе
с базой, настройками и всем остальным.

```bash
# на хосте Proxmox, где 100 - номер твоей VM
qm snapshot 100 before-update --description "перед обновлением 2 сентября"

# посмотреть список
qm listsnapshot 100

# откатиться
qm rollback 100 before-update
```

То же самое есть в панели: вкладка **Snapshots** у виртуалки.

`git` откатывает код. Снапшот откатывает **всё** — включая неудачную
миграцию базы, сломанные настройки Docker и «я что-то не то удалил».
Для человека, который правит сервер по подсказкам нейросети, это лучшая
страховка из существующих.

**Привычка:** снапшот перед каждым `./deploy.sh`, который несёт что-то
серьёзнее правки текста. Старые снапшоты удаляй — они занимают место
и замедляют диск.

## Бэкапы: нужны оба уровня

Это разные инструменты для разных бед, и один другой не заменяет.

### Уровень 1. Проксмоксовский бэкап всей машины

Панель: **Datacenter → Backup → Add**. Расписание — ночью, режим
**Snapshot**, хранить 7 копий.

Спасает от: сдох диск, снёс машину, «всё сломалось непонятно как».
Восстановление — вся виртуалка целиком, как была.

**Важная оговорка.** Бэкап работающей машины в режиме Snapshot делает
снимок диска на лету. Для базы SQLite это примерно как выдернуть питание:
файл окажется целым, но последние транзакции могут не попасть.
Для аварийного восстановления это приемлемо. Как источник правды
по платежам — нет. Поэтому нужен второй уровень.

### Уровень 2. Бэкап самой базы

В проекте есть `./backup.sh`. Он делает горячий бэкап через `sqlite3`,
и это не то же самое, что скопировать файл.

**Почему просто `cp data/app.db` — ошибка.** База работает в режиме WAL:
свежие записи какое-то время лежат в отдельном файле `app.db-wal`
и ещё не перенесены в основной. Копия основного файла в такой момент —
целая, но устаревшая база. Вот замер на живой базе с 500 платежами:

```
cp data/app.db      → в копии 495 платежей   ← пять потеряны молча
./backup.sh         → в копии 500 платежей
```

Потеря тихая: файл открывается, база рабочая, просто в ней нет части
вчерашних денег. Узнаешь об этом в тот день, когда бэкап понадобится.

`deploy.sh` вызывает `backup.sh` сам. Отдельно повесь его на ночь:

```bash
crontab -e
```

```
0 4 * * * cd /opt/app && ./backup.sh >> /var/log/kartochka-backup.log 2>&1
```

### Уровень 3, без которого первые два не считаются

**Копия за пределами дома.** Пожар, кража, скачок напряжения — и Proxmox
вместе со всеми бэкапами на нём перестаёт существовать.

Раз в неделю забирай базу себе на ноутбук:

```bash
scp пользователь@АДРЕС_VM:/opt/app/backups/app-*.db ~/Downloads/
```

Или настрой отправку в российское объектное хранилище (Selectel, Yandex
Object Storage) — попроси Claude настроить, это несложно.

Раз в квартал **проверяй, что бэкап открывается**. Непроверенный бэкап —
это не бэкап, а надежда:

```bash
sqlite3 ~/Downloads/app-2026-09-02.db "SELECT count(*) FROM users;"
```

## Чтобы всё поднималось само

**Автозапуск виртуалки.** В панели: виртуалка → **Options → Start at boot →
Yes**. Иначе после скачка напряжения Proxmox поднимется, а сервис нет.

**Автозапуск контейнера.** Уже настроен: `restart: unless-stopped`
в `docker-compose.yml`.

**ИБП.** Минут на 20 хватит: он переживает мигания света, которые и есть
основная причина внезапных выключений.

**Знать о падении.** Поставь внешний мониторинг, который дёргает твой сайт
раз в минуту и пишет в Telegram, если тот не ответил. Сервисов бесплатных
хватает. Узнавать о падении от клиента — плохо.

## Обновления Proxmox

Раз в пару месяцев:

```bash
apt update && apt dist-upgrade
```

Учти: Proxmox VE 8 снимается с поддержки 31 августа 2026 — если у тебя
восьмая ветка, планируй переход на девятую.

Без платной подписки при обновлении будет всплывать окно «нет валидной
подписки». Это нормально, обновления доступны и так.
