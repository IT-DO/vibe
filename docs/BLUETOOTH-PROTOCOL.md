# Протокол печати Xiaomi Portable Photo Printer 1S

Разобрано по журналу Bluetooth с настоящей печати (Redmi Note 8 Pro,
MIUI 12.5, приложение Xiaomi Home, один отпечаток). Журнал: 4143 пакета
HCI, 263 секунды. Инструмент разбора — `tools/btsnoop-analyze.py`.

## Главное: это Bluetooth Classic, а не BLE

Принтер работает **не по Bluetooth Low Energy**. Канал ATT в журнале не
встречается вовсе. Обмен идёт по классическому Bluetooth:

```
L2CAP PSM 0x0003 (RFCOMM) -> DLCI 4 -> последовательный поток
```

То есть это обычный **Serial Port Profile (SPP)**: принтер выглядит как
последовательный порт, в который пишут байты.

Практический вывод: библиотеки для BLE (`react-native-ble-plx` и подобные)
к этому принтеру неприменимы — он даже не появится в списке BLE-устройств.
Нужен Bluetooth Classic и сопряжение через системные настройки.

## Формат кадра

Поток SPP нарезан на кадры. Заголовок 20 байт, все числа — little-endian.

| Смещение | Размер | Что |
|---|---|---|
| 0 | 1 | `0x7E` — начало кадра |
| 1–2 | 2 | `0x64 0x00` — версия протокола |
| 3 | 1 | канал: `0xFF` рукопожатие, `0x03` команды, `0x04` данные изображения |
| 4 | 1 | команда |
| 5 | 1 | признак направления/типа (`0x02`, `0x03`, `0x06`) |
| 6–9 | 4 | номер пакета, сквозной счётчик с 1 |
| 10–13 | 4 | идентификатор сообщения |
| 14–15 | 2 | всего частей (у данных изображения) |
| 16–17 | 2 | номер части, с 1 |
| 18 | 1 | младшие 8 бит длины данных |
| 19 | 1 | атрибуты; **младшие 2 бита — старшие биты длины** |
| 20… | N | данные |
| +N | 1 | контрольная сумма |
| +N+1 | 1 | `0x7E` — конец кадра |

**Длина = байт[18] + ((байт[19] & 0x03) << 8)**, то есть до 1023 байт.
Формула проверена на всех 270 кадрах журнала.

Байт-стаффинга нет: `0x7E` свободно встречается внутри данных. Поэтому
границы кадров ищутся по началу `7E 64 00` вместе с возрастающим номером
пакета, а не по завершающему байту.

## Рукопожатие

```
телефон -> принтер   канал 0xFF, команда 0x10   "hello"
принтер -> телефон   канал 0xFF, команда 0x11   32 00 00 00 + 32 hex-символа
телефон -> принтер   канал 0xFF, команда 0x12   16 hex-символов + 16 байт
принтер -> телефон   канал 0xFF, команда 0x13   "ok"
```

Принтер представляется строкой из 32 шестнадцатеричных символов (16 байт) —
это его идентификатор. Телефон отвечает 32 байтами: 16 печатных символов и
16 двоичных.

## Передача отпечатка

Данные идут по каналу `0x04`, разбитые на части: в разобранном журнале
**227 частей, 224 432 байта**. Все части по 992 байта, последняя — 240.
В заголовке каждой части стоит «всего частей» и «номер части», так что
порядок восстанавливается на приёмной стороне.

По каналу `0x03` до и после передачи идут команды — 42 кадра по 48–112
байт.

## Шифрование

Данные зашифрованы. Это видно сразу:

- энтропия 7,999 бит/байт — неотличимо от случайного шума;
- zlib сжимает всего на 2 %;
- сигнатуры JPEG (`FF D8 FF`) нет, стаффинга `FF 00` нет.

Но шифр — **блочный, 16 байт, в режиме ECB**, и это доказывается прямо по
журналу. Командные кадры длиной 48 байт (три блока) выглядят так:

```
кадр 4:  c421c9ff ef5812d6 b07516b3 fffaa758 | 19871c8d… | e50fd3d7 …297f
кадр 5:  c421c9ff ef5812d6 b07516b3 fffaa758 | 1848f646… | e50fd3d7 …297f
кадр 6:  c421c9ff ef5812d6 b07516b3 fffaa758 | 86656f93… | e50fd3d7 …297f
```

Первый и третий блоки совпадают байт в байт, средний — разный. Так ведёт
себя только ECB: одинаковый блок открытого текста всегда даёт одинаковый
блок шифротекста.

В данных изображения — 303 повтора 16-байтных блоков на 14 027 блоков, с
характерным шагом **176 байт** (11 блоков). Для случайных данных такое
невозможно; 176 байт — это, судя по всему, длина строки растра.

### Ключ

Ключ уникален для устройства: по публичному разбору родственной модели
(`XMKDDYJ01HM`) им служит **miio-токен принтера**. Подбор по данным
рукопожатия не даёт результата — проверены прямые значения, MD5, SHA-1,
SHA-256 и их сочетания, для AES-ECB и для RC4.

Токен принадлежит владельцу устройства и извлекается из его аккаунта
Xiaomi — например, утилитой Xiaomi-cloud-tokens-extractor или из Home
Assistant, если принтер туда добавлен.

## Что известно о самом изображении

Родственная модель принимает **baseline JPEG 1040 × 1560** со стандартными
таблицами Хаффмана. Для 1S это ещё предстоит подтвердить: 224 432 байта
зашифрованных данных не противоречат JPEG такого размера.

## Чего пока не хватает

| Что | Зачем |
|---|---|
| miio-токен принтера | расшифровать журнал и проверить гипотезы |
| Команды канала `0x03` в открытом виде | начало задания, размеры, подтверждение |
| Точный алгоритм и режим шифра | AES-128-ECB — предположение по длине блока |
| Формат и размеры изображения | 1040 × 1560 — по родственной модели |

С токеном всё это проверяется за один прогон: команды должны расшифроваться
в осмысленный JSON, а данные изображения — начаться с `FF D8 FF`.
