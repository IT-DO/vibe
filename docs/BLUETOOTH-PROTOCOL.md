# Протокол печати Xiaomi Portable Photo Printer 1S

Протокол разобран полностью и реализован в `src/printing/hannto`. Печать
работает без учётной записи Xiaomi и **без miio-токена**: ключ шифрования
вырабатывается заново при каждом подключении.

Основа разбора — журнал Bluetooth с настоящей печати (Redmi Note 8 Pro,
MIUI 12.5, приложение Xiaomi Home, один отпечаток): 4143 пакета HCI,
263 секунды. Инструмент разбора — `tools/btsnoop-analyze.py`. Сеанс из
этого журнала расшифрован целиком, и его кадры лежат в
`src/printing/hannto/__tests__/fixtures/capture.json` — тесты сверяются
именно с ними, байт в байт.

## Главное: это Bluetooth Classic, а не BLE

Принтер работает **не по Bluetooth Low Energy**. Канал ATT в журнале не
встречается вовсе. Обмен идёт по классическому Bluetooth:

```
L2CAP PSM 0x0003 (RFCOMM) -> DLCI 4 -> последовательный поток
```

То есть это обычный **Serial Port Profile (SPP)**: принтер выглядит как
последовательный порт, в который пишут байты.

Практический вывод: библиотеки для BLE (`react-native-ble-plx` и подобные)
к этому принтеру неприменимы — он даже не появится в списке BLE-устройств.
Нужен Bluetooth Classic и сопряжение через системные настройки. Приложение
использует `react-native-bluetooth-classic` в двоичном режиме соединения
(`connectionType: 'binary'`): режим по умолчанию режет поток по переводу
строки и декодирует как текст, а в кадрах встречается любой байт.

## Формат кадра

Поток SPP нарезан на кадры. Заголовок 20 байт, все числа — little-endian.

| Смещение | Размер | Что |
|---|---|---|
| 0 | 1 | `0x7E` — начало кадра |
| 1–2 | 2 | `0x64 0x00` — версия протокола |
| 3 | 1 | канал |
| 4 | 1 | тип сообщения |
| 5 | 1 | кодировка тела |
| 6–9 | 4 | номер кадра, сквозной счётчик с 1 |
| 10–13 | 4 | номер сообщения |
| 14–15 | 2 | всего частей |
| 16–17 | 2 | номер части, с 1 |
| 18–19 | 2 | атрибуты: длина тела и режим шифрования |
| 20… | N | тело |
| +N | 1 | контрольная сумма |
| +N+1 | 1 | `0x7E` — конец кадра |

**Каналы**: `0` базовый, `1` данные, `2` файл, `3` команды под шифром,
`4` файл под шифром, `255` рукопожатие.

**Тип сообщения**: `6` запрос, `7` ответ, `16`–`19` четыре шага
рукопожатия.

**Кодировка**: `1` двоичная, `2` шестнадцатеричная, `3` JSON.

### Поле атрибутов

Два байта совмещают длину и режим шифрования:

```
атрибуты = длина + 5120 (AES-ECB) [+ 8192, если частей больше одной]
длина    = атрибуты < 8192 ? атрибуты % 1024 : (атрибуты - 8192) % 1024
```

Под длину отведено 10 бит, то есть **не больше 1023 байт**. Отсюда и
размер куска файла: 992 байта тела — самое большое кратное 16 (шифр
блочный), которое туда влезает.

### Контрольная сумма

Сумма всех байтов кадра минус **одна** начальная метка:

```
кадр[-2] = (сумма(кадр) - 0x7E) & 0xFF
```

Считается, когда сама сумма и завершающая метка ещё нулевые, — поэтому в
неё попадает только начальная метка. Легко ошибиться и вычесть обе.

Байт-стаффинга нет: `0x7E` свободно встречается внутри шифротекста.
Поэтому границы кадров ищутся по началу `7E 64 00` и длине из заголовка, а
не по завершающему байту.

## Рукопожатие: Диффи — Хеллман

```
телефон -> принтер   канал 255, тип 16   "hello"
принтер -> телефон   канал 255, тип 17   G(4) | P(16) | RA(16)
телефон -> принтер   канал 255, тип 18   RB(16) | AES(ключ, P)(16)
принтер -> телефон   канал 255, тип 19   "ok"
```

Ключ вырабатывается заново при каждом подключении и нигде не хранится.
**Никакого токена не нужно** — печатать может любой, кто дотянулся до
принтера по Bluetooth.

### Числа передаются ASCII-текстом

Особенность прошивки, без которой ничего не сходится: большие числа
передаются не двоичными, а **строкой шестнадцатеричных цифр**. Байты
`45 36 39 36` — это символы «E696», то есть число `0xE696`. Из-за этого
16-байтное поле несёт всего 64 бита.

### Выработка ключа

```
b     — наш случайный секрет, 2 < b < P
RB    = G^b mod P          -> ASCII-запись, выровнена вправо в 16 байтах, слева «0»
общий = RA^b mod P         -> ASCII-запись, выровнена влево в 16 байтах, справа 0x00
ключ  = первые 16 байт этой записи
```

Принтер проверяет нас тем, что мы возвращаем его же модуль `P`,
зашифрованный общим ключом.

### Стойкость

Модуль, который выдаёт прошивка, **не простое число**:

```
P = 0xE6969D3D495BE32C = 2² · 7³ · 83 · 179 · 270833 · 3009749
```

Он составной и гладкий, поэтому дискретный логарифм решается методом
Похлига — Хеллмана за доли секунды. Именно так и был восстановлен секрет
записанного сеанса (`b = 4126797477100135`), а вместе с ним ключ
`8E3B9E8E9AFD85B0` — и весь журнал расшифрован.

Для приложения это не проблема: по Bluetooth к принтеру и так подключается
кто угодно. Но полагаться на это шифрование как на защиту нельзя, и знать
об этом стоит.

## Шифрование тела

**AES-128-ECB с дополнением нулями** (не PKCS#7). Ключ — выработанный при
рукопожатии, как есть, 16 байт ASCII.

Режим ECB виден прямо в журнале: командные кадры длиной 48 байт имеют
байт-в-байт одинаковые первый и третий блоки при разном среднем — так
ведёт себя только ECB.

Расшифровка отбрасывает хвостовые нули: это дополнение шифра, а не данные.

## Команды

Канал 3, тип 6 (запрос) / 7 (ответ), кодировка JSON, тело зашифровано.

Принтер нумерует свои ответы **собственным счётчиком**, не нашим, поэтому
сопоставлять ответ с запросом надо по полю `id` внутри JSON.

```jsonc
// кто ты
{"method":"get_prop","id":3,"params":["device_info"]}
{"result":[{"fw_ver":"2.1.2_0015","hw_ver":"REVB","sku":"BHR9974GL",
            "mac":"...","did":"...","sn_all":"..."}],"id":3}

// как себя чувствуешь
{"method":"mixed_status","id":4,"params":{}}
{"result":{"category":"idle","sub_category":"init","error":0,
           "battery":3,"battery-level":83,"clean_remain":6},"id":4}

// прими задание
{"method":"print_job","id":18,
 "params":{"file_size":223524,"copies":1,"job_type":0,"channel":528}}
{"result":{"job_id":15},"id":18}

// чем кончилось
{"method":"job_info","id":265,"params":[15]}
{"result":[{"job_id":15,"job_state":"finished","prt_copies":1,
            "transfer_time":8727,"print_time":51777}],"id":265}
```

`category` по ходу печати: `idle` -> `processing` (`sub_category`:
`decoding`, затем печать) -> `idle`. `error` = 0, когда всё в порядке.

Принтер шлёт и незапрошенные события (`event.big_data`) — у них нет `id`,
и приложение их пропускает.

## Передача отпечатка

Канал 4, тип 6, кодировка шестнадцатеричная, тело зашифровано, кадр
помечен номером части и их общим числом.

```
кусок = job_id (4 байта, младшим вперёд) + до 988 байт данных
тело  = AES-ECB(ключ, кусок)                     -> 992 байта
```

Принтер **не подтверждает куски по одному** — он просто читает поток.
Официальное приложение склеивает по три кадра в одну запись; приложение
делает так же: 227 отдельных записей в нативный модуль — это 227 переходов
через мост React Native.

Последний кусок дополняется нулями до кратности 16. Принтер знает длину
файла из `print_job` и лишнее отбрасывает — поэтому `file_size` там
обязателен.

В разобранном журнале: 227 частей, 223 524 байта, передача 8,7 секунды,
печать 51,8 секунды.

## Изображение

**Baseline JPEG, ровно 1040 × 1560 пикселей**, 8 бит, 3 компонента
(YCbCr). Подтверждено маркером SOF0 расшифрованного файла из журнала.

На бумаге 50,8 × 76,2 мм это **520 dpi**. Приложение готовит лист ровно
такого размера: картинку больше принтер не уменьшает, а **обрезает по
центру**, молча теряя края отпечатка.

- [tuat-yate/xiaomi-photo-printer](https://github.com/tuat-yate/xiaomi-photo-printer)
  — разбор модели Pro, та же схема. Сверка подтвердила все константы,
  формулу контрольной суммы и выработку ключа; оттуда же склейка кадров по
  три и то, что принтер обрезает изображение, а не масштабирует.

  miio-токен. К 1S неприменимо.
